# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AppBlips is a React SPA that generates small single-file HTML apps (and, in website mode, multi-page sites of standalone HTML pages) from a text prompt via an OpenAI-chat-completions-compatible LLM API, then renders them live in a sandboxed preview iframe. The builder calls `/api/chat`; its endpoint, key, model, and tuning knobs are fixed server-side. AI-enabled generated apps use a distinct bridge and either hosted relay, self-hosted BYOK, or self-hosted relay behavior. See "LLM proxy" and "Generated-app AI" below.

The app runs in one of two modes, chosen entirely by env vars (see "Hosting modes: self-hosted vs. Firebase-hosted" below) — there's no runtime toggle:
- **Self-hosted** (default): single local user, no sign-in, no cloud sync, no deploy-to-public-URL. Nothing talks to Firebase.
- **Hosted**: Firebase Auth + Firestore (projects, deployments) + Storage (deployed HTML), fronted by a Cloudflare Pages Function that verifies ID tokens before relaying to the LLM.

## Commands

- `npm run dev` — start Vite dev server (port 5175, `host: true` for LAN/devcontainer access)
- `npm run build` — production build
- `npm run lint` — ESLint (flat config, `eslint.config.js`)
- `npm run preview` — preview the production build

There is no automated test suite wired to `npm test`. `testing/` holds standalone scripts run directly with node (e.g. `node testing/testChatProxy.js`, `node testing/test-ai-relay.js`) that exercise the chat proxy, AI relay/bridge/session logic, and preview behavior — not a CI-run suite.

## Architecture

The app is split into `App.jsx` (workspace/generation state + composition), `src/lib/` (framework-free logic), `src/hooks/` (stateful concerns), and `src/components/` (presentational UI):

- **[src/App.jsx](src/App.jsx)** — the `App` component: owns the workspace/generation state (prompt, `files`/`activePage` — `generatedCode` is derived as the landing page, `versions`/undo-redo, streaming refs, `handleGenerate`, naming/new-app flow, `resetCurrentWorkspace`) and composes everything else.
- **[src/previewBridge.js](src/previewBridge.js)** — a self-contained script injected into the generated app's HTML at render time, documented in detail in its file header.
- **[src/firebase.js](src/firebase.js)** — the single Firebase SDK init point, gated on `firebaseEnabled` (`SELF_HOSTED_MODE === 'false'`). When disabled, `app`/`auth`/`db`/`storage` all stay `null` and no Firebase code (including the App Check network call) runs.
- **src/lib/** — pure logic, no React:
  - `llm.js` — `requestModelText` / `generateAppCode` / `generateClarifyingQuestion` (the API layer; attaches the Firebase ID token + App Check token to every `/api/chat` call)
  - `pages.js` — multi-page helpers: `files` map (`{'index.html': html, 'about.html': html}`; `index.html` is always the landing page), page-name validation, `resolvePageLink`, `findBrokenLinks`, size/page limits (12 pages, 400 KB per version), `formatFilesForPrompt`. `pageTools.js` — `executeFilesTool` (the `file`-routed edit tools plus `create_page`/`delete_page`/`list_pages`) and `checkSyntaxFiles`; kept free of Firebase imports so node tests can load it. `siteRouter.js` — the in-document page router shared by the password-unlock wrapper and the new-tab shell. `zip.js` — dependency-free store-only ZIP writer for multi-page export.
  - `edits.js` — `sanitizeHtmlResponse` + the surgical-edit engine (`applySurgicalEdits` and friends)
  - `prompts.js` — system prompts and tool schemas; `constants.js` — presets, `PREVIEW_MODES`, marquee/streaming constants
  - `config.js` — theme/UI-preference persistence helpers; `helpers.js` — syntax highlighter, preview-box math, misc
  - `syntaxCheck.js` — Acorn-based JS syntax check for generated `<script>` blocks; `markdown.js` — small dependency-free markdown renderer for chat transcript text
  - `deploy.js` — public-URL deployment (Firestore `deployments` doc + Storage upload); `projectsStorage.js` — localStorage↔Firestore project row plumbing
  - `crypto.js` — client-side PBKDF2/AES-GCM encryption for password-protected deploys, wrapping the HTML in a standalone unlock-screen page
  - `pwa.js` / `analytics.js` / `seo.js` — snippets spliced into deployed HTML at deploy time (and re-injected at serve time in `functions/[[path]].js`) for installability, Umami analytics (hosted mode only), and noindex/favicon tags
  - `pendingJob.js` — persists an in-flight generation to `localStorage` so an interrupted build can be detected and offered for retry on next load
  - `auth/` — the auth adapter; see "Hosting modes" below
- **src/hooks/** — `useTheme`, `useChatFont`, `useAuth` (session + one-time local→cloud import offer), `useProjects` (list/persistence/resume), `useDeployment`, `usePageNavigation` (parent-side page history for multi-page previews), `usePreviewViewport` (mode/orientation/zoom), `useBuildPaneResize`, `usePreviewBridge` (the postMessage driver).
- **src/components/** — `Header`, `HistorySidebar`, `BuildPanel` (with `StarterIdeas`, `ChatTranscript`, `PromptInput`), `PreviewPane` (with `DeviceMockup`, `CodeView`), `SplashScreen`, `AuthToast`, and modals: `Modal`/`ConfirmModal` (shared shells), `SettingsModal`, `ProjectsListModal`, `DeployModal`, `NamingModal`, `AuthModal`, `ImportModal`, `AccountSettingsModal`. Self-contained modals (`AuthModal`, `SettingsModal`, `AccountSettingsModal`) own their form state and talk to `firebase`/`lib/config` directly. Auth-related UI (`AuthModal`, sign-in affordances in `Header`) only renders when `firebaseEnabled`.

### Hosting modes: self-hosted vs. Firebase-hosted

One env var, `SELF_HOSTED_MODE`, drives both the browser bundle ([src/firebase.js](src/firebase.js)) and the server-side proxy (`functions/_lib/chatProxy.js`), even though those are two different runtimes: it has no `VITE_` prefix (unlike `VITE_FIREBASE_*` below), but `vite.config.js`'s `envPrefix` explicitly allow-lists it into `import.meta.env` too, alongside the default `VITE_` prefix. Default is unset/anything other than `"false"` = self-hosted; set `SELF_HOSTED_MODE=false` for hosted mode.
- Self-hosted: [src/lib/auth/mockAuthProvider.js](src/lib/auth/mockAuthProvider.js) supplies a single fixed always-signed-in `local-user`; every method besides `onAuthStateChanged` is a no-op (auth UI never renders in this mode, so they're unreachable in practice). `/api/chat` treats every request as that same local user and performs no token check — self-hosters exposing the app beyond localhost are responsible for their own access control.
- Hosted: [src/lib/auth/firebaseAuthProvider.js](src/lib/auth/firebaseAuthProvider.js) backs real sign-in (email/password, GitHub, Google) via Firebase Auth. `/api/chat` requires a valid Firebase ID token (verified server-side via the `accounts:lookup` REST endpoint) and a valid Firebase App Check token (verified via Google's App Check JWKS endpoint); a missing/invalid token gets a 401. Projects sync to Firestore (`projects` collection) and deploys go through Firestore (`deployments` collection, slug → storage path) + Storage (`orion-deploys` bucket) — see `firestore.rules`/`storage.rules` for the per-user ownership checks.
- [src/lib/auth/index.js](src/lib/auth/index.js) picks between the two providers based on `firebaseEnabled`; `useAuth`/`AuthModal`/`llm.js`/etc. only ever import from `lib/auth`, never the concrete providers, so they stay unaware of which is active.
- On first sign-in in hosted mode, `useAuth`'s import flow offers to migrate any `localStorage['orion-projects']` rows into Firestore (one-time per user, flagged via `orion-imported-<uid>`).

### Generation flow

1. **Initial generation** (`generatedCode` is empty): `buildInitialGenerationPrompt` builds a layout-specific instruction (mobile/desktop/both), sent with `HTML_SYSTEM_PROMPT` as a single non-tool completion. The response is cleaned by `sanitizeHtmlResponse` (strips markdown fences, finds `<!DOCTYPE html>`/`<html>` boundaries) to get raw HTML.
2. **Refinement** (`generatedCode` already exists): switches to a "surgical edit" loop. The model is forced (`tool_choice`) to call `apply_surgical_edits` with search/replace blocks anchored on `<!-- @section: name -->` landmark comments. `applySurgicalEdits` tries an exact string match first, then a whitespace-normalized fuzzy line-by-line match. On failure it retries up to 3 times, feeding the error back to the model as corrective context (`generateAppCode`'s self-healing loop).
3. Both paths go through `requestModelText`, which POSTs to `/api/chat` (same-origin proxy, see "LLM proxy" below) with exponential backoff retry (`delays` array) and supports SSE streaming (`onChunk`) with a 60s stall timeout, accumulating both text deltas and `tool_calls` deltas.

**Multi-page websites (website mode only).** Every version stores `files` (page filename → full HTML) rather than a single string; `versionFiles()` reads legacy `code`-only versions. The initial build still emits only `index.html`; if its navigation links to pages that don't exist, `createMissingPages` (`llm.js`) creates each with a forced `create_page` call, given the landing page as design context. Refinement uses `getRefinementTools('website')`: `apply_surgical_edits`/`view_code`/`list_sections` take a `file` (null = landing), plus `create_page`/`delete_page`/`list_pages`, and the loop refuses to finish while a page links to a missing page (`MAX_LINK_REPAIR_ATTEMPTS`). Any new tool name must be added to `ALLOWED_TOOL_NAMES` in `chatProxy.js`. Internal links are relative filenames (`about.html`, `index.html#contact`).

Each successful generation/edit is pushed onto a `versions` array (undo/redo via `currentVersionIndex`); going back and generating again truncates future versions, like standard undo history. `pendingJob.js` records the in-flight prompt/project before each generation starts so an interrupted build (tab closed mid-stream) can be detected and retried on next load.

### Preview isolation (security-critical — read before touching this)

The generated app's HTML is never rendered directly. `injectPreviewBridge` (in `previewBridge.js`) splices a bridge `<script>` into the head/html/body of `generatedCode` at render time only, producing `srcDoc` fed to an iframe that has `sandbox` **without** `allow-same-origin` — the frame's origin is opaque, so the parent cannot reach `iframe.contentDocument` and generated code cannot reach the parent.

Consequences that matter when editing this code:
- The bridge is computed in a `useMemo` in `App.jsx` and is **never** written back into `generatedCode`. It must stay out of downloads, the clipboard, the code panel, `localStorage['orion-projects']`, and especially out of reach of `applySurgicalEdits`'s fuzzy matcher (which would otherwise happily "fix" bridge code during a refinement pass).
- Multi-page previews: the bridge intercepts clicks on relative links, `postMessage`s `navigate-page` with the raw href, and the parent (`usePageNavigation`) resolves it against `files` and swaps `srcDoc` — the frame never navigates. Each page swap resets the frame's own history, so page back/forward lives in the parent and is combined with the frame's hash history for the nav buttons.
- Parent↔frame communication is `postMessage` only, authenticated by a per-render random `token` plus checking `event.source === iframe.contentWindow` (never `event.origin`, which is always the string `"null"` for an opaque origin). `targetOrigin: '*'` is required and is safe only because the protocol never carries a secret — don't add one.
- The bridge shims `localStorage`/`sessionStorage`/`document.cookie` inside the frame (real APIs throw `SecurityError` on an opaque origin); `localStorage` is hydrated from project-scoped storage (`orion-preview-storage:<projectId>`) and syncs mutations over postMessage, preserving data across reloads and revisions. The bridge also implements the mobile touch-scroll/momentum simulation, toggled on/off via a `configure` message keyed to `previewMode === 'mobile'`.
- `BRIDGE_SOURCE` is checked at module load to contain no literal `</`, which would truncate the injected `<script>` tag.

### LLM proxy

- The LLM base URL, API key, model, `max_tokens`, and temperature are **not** user-configurable in the UI — they're read server-side from `APPBLIPS_LLM_BASE_URL` / `APPBLIPS_LLM_API_KEY` / `APPBLIPS_LLM_MODEL` / `APPBLIPS_LLM_MAX_TOKENS` / `APPBLIPS_LLM_TEMPERATURE` env vars (see `.env.example`). `APPBLIPS_LLM_TEMPERATURE` defaults to `0.2` when unset. None are `VITE_`-prefixed, so Vite never inlines them into the client bundle. Reasoning effort is the exception: it's a per-user preference (`orion-reasoning-effort` in `localStorage`, surfaced in `SettingsModal`) sent by the client as `reasoning_effort` for the initial-generation, refinement-loop, and ask calls (auto-fix, clarifying questions, and the intro/completion chat replies stay pinned to `'none'`). Before the request leaves the server, `applyReasoningSetting` (`functions/_lib/reasoning.js`) translates that value into the wire format the configured provider expects: OpenAI-compatible/DeepSeek keep `reasoning_effort` as-is (DeepSeek maps `medium`→`high` itself), while Z.ai GLM gets a `thinking: {type}` toggle (`disabled` for off) plus `reasoning_effort` only on GLM-5.2+, with `medium`→`high` (GLM-5.3 has no medium) and `stream_options` dropped (not in Z.ai's schema). The provider is auto-detected from `APPBLIPS_LLM_MODEL`/`APPBLIPS_LLM_BASE_URL` or pinned via `APPBLIPS_LLM_PROVIDER` (`openai`/`deepseek`/`zai`); unknown configs keep the original pass-through. The same helper backs the generated-app relays via `APPBLIPS_APP_LLM_PROVIDER`, and its returned `reasoningEnabled` flag drives the forced-`tool_choice`→`'auto'` downgrade (thinking backends reject named/required choices with 400, and Z.ai rejects them unconditionally — its schema only accepts `'auto'`).
- `functions/_lib/chatProxy.js` (`handleChatProxy(request, env)`) is the single implementation of the proxy: it builds the upstream OpenAI-style request from env + the client's `{ messages, tools, tool_choice, stream, reasoning_effort }` body, and streams the upstream response straight back — it's a transparent relay, not a reimplementation, so `requestModelText`'s SSE-parsing/retry logic in `src/lib/llm.js` is unaware a proxy exists. It no longer reads `APPBLIPS_LLM_REASONING_EFFORT`; a missing client value defaults to `'none'`.
- In **hosted mode** (`SELF_HOSTED_MODE=false`), every request must carry a valid Firebase ID token (verified against Firebase's `accounts:lookup` endpoint plus `FIREBASE_API_KEY`) and a valid Firebase App Check token (verified against Google's App Check JWKS endpoint using `FIREBASE_PROJECT_NUMBER`/`FIREBASE_PROJECT_ID`); a missing or invalid token is rejected with 401 before the request reaches the LLM. Enforcement can be toggled with `FIREBASE_APPCHECK_ENFORCE=false` if needed. In **self-hosted mode** (default), there is no token check at all — anyone who can reach `/api/chat` spends the configured LLM budget, so self-hosters exposing this beyond localhost need their own access control in front of it. `checkRateLimit` is a real per-user limiter (defaults 60 requests / 300s via `APPBLIPS_CHAT_RATE_LIMIT_MAX`/`APPBLIPS_CHAT_RATE_LIMIT_WINDOW_SECONDS`, 429 + `Retry-After`), but it lives in an in-memory `Map`, so on Cloudflare Pages it is per isolate and best-effort, not a hard billing boundary. In self-hosted mode it keys on the single shared `local-user`.
- **Hosted-only request hardening** (all skipped when self-hosted, which stays a transparent relay): after auth and the rate limiter, `handleChatProxy` caps the body at 2 MB (`APPBLIPS_CHAT_MAX_BODY_BYTES`, 413), validates `messages` (non-empty array, at most 100 via `APPBLIPS_CHAT_MAX_MESSAGES`, roles system/user/assistant/tool, string or text/image_url content), restricts `tools`/`tool_choice` to the four names in `prompts.js` (`apply_surgical_edits`, `ask_clarifying_questions`, `view_code`, `list_sections` — add new tools to `ALLOWED_TOOL_NAMES` in `chatProxy.js` or hosted mode will 400 them), restricts `reasoning_effort` to a known set, and always sets `max_tokens` (falls back to 32768 when `APPBLIPS_LLM_MAX_TOKENS` is unset). Violations return 400/413. The preview's generated-app AI bridge (`usePreviewBridge.js`) also goes through `/api/chat`, sending up to 64 plain-text messages, so keep the message cap above that.
- In production (Cloudflare Pages) this runs as the Pages Function `functions/api/chat.js`, which just calls `handleChatProxy`. `functions/[[path]].js` is a separate, unrelated Function serving deployed user apps on a second hostname (`my.appblips.com`) — don't conflate the two.
- In local dev (`npm run dev`, plain Vite — Pages Functions don't run under Vite), `vite.config.js` registers dev-server middleware on `/api/chat` that calls the same `handleChatProxy`, forwarding the `authorization` and `x-firebase-appcheck` headers and reading env via `loadEnv(mode, cwd, '')` from a local `.env`. This keeps `npm run dev` working with no `wrangler` dependency and no behavior drift between dev and prod.
- Cloudflare Pages deployments need the same env vars set under Settings → Environment variables (`APPBLIPS_LLM_API_KEY` and, in hosted mode, `FIREBASE_API_KEY`, which is Firebase's public web key so it doesn't need to be Secret; restrict it in Google Cloud Console instead) — nothing in the app config does this automatically.
- Projects are persisted to `localStorage['orion-projects']` as `{id, name, data: {versions, currentVersionIndex}, updatedAt}` rows in self-hosted mode (or as the pre-import cache in hosted mode); the last-open project id is in `localStorage['orion-current-project-id']`.

### Deploy-to-public-URL (hosted mode only)

- `deploy.js` uploads the site's `files` (never the preview bridge). Layout: landing at `<uid>/<token>.html`, extra pages at `<uid>/<token>/<page>.html`, and the `deployments/{slug}` doc carries `page_names` (extra pages, stored as filenames like `about.html`; the serving Function strips the extension via `parseDeploymentDoc`, since URLs and storage paths use the bare name) and `bundle`. `testing/testDeployServing.js` covers the serving path with the real stored shape. Public URLs are `/<slug>` and `/<slug>/<page>`; `functions/[[path]].js` (`candidatesForPath`) tries the whole path as a `user/slug` first so existing links keep their meaning, then slug + page. It rewrites internal page links to absolute `/<slug>/<page>` at serve time (`rewritePageLinks`; a slug URL has no trailing slash, so relative links would break) and injects `window.__APPBLIPS_SLUG__`, which `pwa.js`, `aiBridge.js` and the unlock wrapper read instead of parsing `location.pathname`. Password-protected multi-page sites are ONE encrypted bundle in the landing object (`bundle: true`, no page objects): a single unlock, then `siteRouter.js` routes between pages client-side. Redeploys delete page objects that are gone (`removeStalePages`). Objects go to the Firebase Storage `orion-deploys` bucket, then `registerDeployment` writes a `deployments/{slug}` Firestore doc mapping the public slug to that storage path ( retries with a random suffix on slug collision).
- The object is deliberately **not** served straight from Firebase Storage's public URL: `functions/[[path]].js` is a Cloudflare Pages Function bound to a dedicated hostname (`my.appblips.com`) that looks up the slug in Firestore via the REST API and re-serves the HTML with a real `text/html` content type and a locked-down CSP (see file header for the full rationale). Deployed apps must stay on this separate hostname — they're LLM-generated code with full script privileges, and on the SPA's own origin they could read `localStorage` (the user's session, and in self-hosted contexts any LLM config).
- Optional deploy-time extras, all spliced into the HTML before upload (and some re-injected at serve time for older deploys): PWA installability (`pwa.js`, plus the `_pwa/{slug}/{manifest.webmanifest,sw.js}` route in `functions/[[path]].js`), Umami analytics (`analytics.js`, hosted mode only), noindex/custom favicon (`seo.js`), and password protection (`crypto.js` — PBKDF2+AES-GCM, wraps the app in a standalone unlock-screen page that decrypts and `document.write`s the real HTML client-side).
- Some in-repo comments still describe the pre-migration Supabase-backed serving story (why a Cloudflare Function is needed to fix `text/plain` responses); the mechanism they explain still applies, but the code path is Firebase Storage + Firestore, not Supabase. A few `src/lib/*` files (`constants.js`, `deploy.js`, `helpers.js`, `projectsStorage.js`) likewise still reference "Supabase" in comments/naming despite operating on Firestore/Storage now.

### Generated-app AI

Projects opt in with an `aiEnabled` boolean (default off), controlled by the AI switch in `BuildPanel`. Prompts teach generated code one stable API: `blip.ai.text(messages, options)`. Exact uppercase `BLIP.AI.TEXT` and legacy `window.ai.chat` aliases are installed for compatibility, but generated code should use lowercase.

**Hosted mode:** enabled previews receive a render-time bridge whose requests cross the token-authenticated, source-checked `postMessage` channel; the parent calls authenticated `/api/chat`. Enabled deployments receive a deploy-time bridge and call same-origin `/ai/chat`. By default that bridge embeds a freshly rotated opaque deployment token (public by design, valid until redeploy). Setting `APPBLIPS_SESSION_SECRET` server-side and `VITE_AI_SESSION_ENABLED=true` at build time switches to short-lived sessions instead: the page mints an HMAC-signed token from `/ai/session` (`functions/_lib/aiSession.js`) and sends it to `/ai/chat`, so a copied page loses access when the token expires or the deployment's `aiTokenGeneration` is bumped (redeploy / AI toggle). `/ai/session` can be gated by Cloudflare Turnstile (`TURNSTILE_SECRET` + `VITE_AI_TURNSTILE_SITE_KEY`, verified in `functions/_lib/turnstile.js`) — that is what actually blocks scripted clients, since Origin is spoofable. `functions/_lib/aiRelay.js` forces server provider settings from the dedicated `APPBLIPS_APP_LLM_*` variables (separate from the builder's `APPBLIPS_LLM_*`), caps payload/output, rejects requests without the deployment's own Origin by default (`APPBLIPS_AI_REQUIRE_ORIGIN`), and rate-limits with two independent best-effort token buckets: per client IP (`APPBLIPS_AI_RATE_LIMIT_*`) and per deployment (`APPBLIPS_AI_DEPLOYMENT_RATE_LIMIT_*`, looser, since it covers every visitor of an app). The per-IP bucket is consumed before the body is buffered and before any Firestore lookup, so unauthenticated callers cannot drive database reads with junk tokens; the per-deployment bucket is consumed only after both that check and token validation pass, so a throttled abuser cannot starve an app's real visitors. The Firestore result caches in `aiRelay.js` are size-capped for the same reason (both are keyed by attacker-supplied input). Hosted customers never see provider keys.

**Self-hosted BYOK (default):** `APPBLIPS_GENERATED_AI_MODE=byok`. `src/lib/selfHostedAiBridge.js` is inserted into enabled previews and exported/new-tab HTML at render/export time, never into project versions. On the first `blip.ai.text` call it opens a built-in endpoint/model/key dialog. Configuration is stored in `sessionStorage` by default or `localStorage` only after explicit opt-in. The key is never bundled into HTML or sent to AppBlips, but it is necessarily available to scripts in the finished app and the provider must support browser CORS. The bridge also exposes `configure`, `isConfigured`, and `clearConfiguration`.

**Self-hosted relay (operator-funded):** `APPBLIPS_GENERATED_AI_MODE=relay` and public `APPBLIPS_APP_AI_RELAY_URL` are build-time client settings. Provider credentials use the server-only `APPBLIPS_APP_LLM_*` variables (shared with hosted mode). `/api/app-ai/chat` is implemented by `functions/_lib/selfHostedAiRelay.js` and wired into Vite, Docker `server.js`, and the Pages-function wrapper. It forces endpoint/model, caps input/output, uses an exact `APPBLIPS_APP_AI_ALLOWED_ORIGINS` CORS allowlist, and rate-limits by client IP with `APPBLIPS_APP_AI_RATE_LIMIT_*`. Same-origin calls are allowed automatically; `Origin: null` is allowed only when explicitly listed. This limiter is not a hard billing boundary.

`generatedAiMode.js` exposes only the safe public mode and relay URL through Vite. Never add `APPBLIPS_APP_LLM_*` to `envPrefix`, log BYOK configuration, persist it in project data, or place any operator provider key in a generated app. Both injected bridge sources retain the no-literal-`</` invariant so they cannot terminate their own script element.


### Preview rendering

`PREVIEW_MODES` defines fixed mobile (399×820) / desktop (1468×1022) viewport presets rendered inside a scaled container; zoom is either auto-fit (recalculated on resize via `previewContainerRef`) or manual (`handleManualZoom`), independent per `previewMode`.

## Security posture

Both `vite.config.js` (dev server headers) and `index.html` (meta CSP) set `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, and a restrictive `base-uri`/`object-src`. `index.html`'s comment block explains why its CSP `<meta>` tag deliberately omits `script-src`: a `srcdoc` iframe inherits the embedder's CSP, so any `script-src` there would break both the generated app's inline scripts/Tailwind CDN tag and (with `'self'`) the dev server's own React-Refresh preamble.

`firestore.rules` and `storage.rules` enforce per-user ownership in hosted mode: a `projects` doc is only readable/writable by its `user_id`; a `deployments` doc is publicly readable (so `functions/[[path]].js` can resolve slugs with no auth) but only its owner can create/update/delete it; Storage objects under `orion-deploys/{userId}/` are publicly readable but writable only by that `userId`.

## Testing Guidelines

- You must ask for permission before using a headless browser (e.g. Playwright, `chromium-cli`) to test changes, every time. Don't launch one on your own initiative, and don't treat an earlier approval, from this session or a past one, as standing permission.
